# Контракты v2: большой склад

Версия 2.0, 07.11.2026. Это подготовительные артефакты, а не готовый backend. Основной layout — `qoima-72x48-v2`. Прежние JSON сохранены в [legacy-v1](legacy-v1/).

## Файлы и статус

| Файл | Назначение |
|---|---|
| `layout.example.json` / `layout.schema.json` | Полная геометрия: 864 адреса, 288 стеллажей, графы, индукции и конвейеры |
| `simulation_defaults.json` | Роли, скорости, времена, конечные вместимости, профили и правила |
| `actors.example.json` / `actors.schema.json` | 24 сотрудника и две связанные с водителями машины |
| `assignment.example.json` | 200 DEMO SKU, 600 партий; иллюстрация, а не обученное ABC-размещение |
| `scenario.schema.json` | Материализованные заказы, поступления и происхождение данных |
| `run.schema.json` | Минимальная полная форма будущего runtime-экспорта |
| `analytical_fixture.json` | Аналитическое ожидание одного полного заказа, а не результат движка |
| `legacy-v1/` | Прежние layout, schema, run, ТЗ и отчёт проверок для 20 SKU |

JSON Schema Draft 2020-12 проверяет форму. Ссылки, количества, геометрия и причинность проверяются отдельно. Большие потоки и полноценный run v2 ещё предстоит создать.

## Работа участников с контрактами

Тилек использует layout, actors и run для сцены и воспроизведения. Арман реализует расчётное ядро, проверку инвариантов и экспорт того же формата.

Оба начинают с одной версии геометрии и аналитической фикстуры. Изменение масштаба не отменяет необходимость общей проверки арифметики до подключения детальных моделей.

## Единицы, идентификаторы и размещение

Формат — UTF-8 JSON, `schema_version="2.0"`. Длины в метрах, время в секундах, координаты `[x,y,z]`, Y вверх. Все ID строковые. SKU, slot, rack, node, actor, vehicle, order и cargo — разные сущности и пространства идентификаторов. NaN, Infinity и скрытое округление недопустимы. Layout и config неизменяемы в пределах прогона.

Активное размещение — взаимно однозначное соответствие slot→SKU: 200 разных SKU занимают 200 из 288 нижних адресов; 88 остаются свободными. Резервное размещение хранится отдельно: у того же SKU ещё две резервные партии. У верхнего адреса `service_node_id=null`; пеший маршрут не поднимается на ярус.

`assignment.example.json` сортирует ячейки по средней геометрической стоимости пути от трёх home и назначает иллюстративные DEMO SKU с номерами 001–200. Это не результат обучения. Рабочее ABC строится по зафиксированным посещениям SKU из training-периода, предшествующего test.

## Layout и транспортные графы

`picker_graph` содержит 184 узла и 205 неориентированных рёбер. Вес ребра равен длине разрешённого прямого отрезка. Примеры ID: `N_A01_Z16`, home `I01`/`I02`/`I03`, буфер `N_REL_BUFFER`. Все нижние адреса достижимы; коробки не являются точками ходьбы. Всего 288 стеллажей × 3 уровня = 864 адреса: 288 для отбора и 576 резервных.

Входной граф `forklift_graphs.inbound`: `FI_HOME=(4,0,44)`, `FI_PICK=(4,0,38)`, `FI_DROP=(4,0,16)`; связи HOME—PICK—DROP. Приёмка и putaway выполняются у сервисных точек площадок. Точная раскладка паллет внутри reserve staging моделируется укрупнённо.

Выходной граф: `FO_HOME=(68,0,10)`, `FO_VIA=(68,0,6)`, `FO_PICK=(66,0,6)`, `FO_TURN=(68,0,2)`, `FO_DROP=(70,0,2)`. Связи: HOME—VIA, VIA—PICK, VIA—TURN, TURN—DROP. Пустой путь до PICK — 6 м, путь с грузом до DROP — 8 м, возврат HOME — 10 м.

Водитель и связанный vehicle следуют одной траектории. Vehicle не считается дополнительным сотрудником.

## Конвейерные ячейки, порты и блокировки

Сегменты конвейера направленные; `from`/`to` находятся на Y=0.9. ID ячейки: `segment_id:index`, индекс от 0 до `cell_count−1`. Груз входит на входной границе ячейки, за 1 с доходит до выходной и при блокировке остаётся там. Центр ячейки не служит точкой телепортации.

| Сегменты | Число ячеек |
|---|---:|
| LOOP_E / TURN_E / LOOP_W / TURN_W | 54 / 2 / 54 / 2 |
| Три FEED | По 1 |
| Шесть BRANCH | По 2 |
| Шесть OUTFEED | По 1 |
| OUT_MAIN | 46 |
| Всего | 179 |

Соединение может находиться внутри длинного сегмента. FEED I01 в `(10,0.9,10)` входит в `LOOP_W:52`; PK01 ответвляется после `LOOP_E:11` при X=20. Соединять только концы сегментов нельзя.

Для порта `offset=distance(from,port)`, индекс следующей ячейки — `offset/cell_length`, предыдущей — `index−1`. Если offset равен длине сегмента, это terminal или следующий сегмент, а не несуществующая `cell[count]`. Все порты расположены на целочисленных границах ячеек.

Расстояние I01→PK01: 1 м feed + 2 м west + 2 м turn + 12 м east + 2 м branch = **19 м**. PK01→shipping: 1 м outfeed + 46 м main = **47 м**.

Один tick: снимок состояния → выбор ходов от выходов к входам → round-robin на слияниях → атомарное применение → приём новых грузов → назначение работ. Каждый ранее находившийся на ленте груз делает не более одного перехода. Tote, введённый в момент t, впервые движется на t+1. Слияние не дублирует cargo.

Полный входной буфер упаковки блокирует ответвление и loop. Автоматической рециркуляции в P0 нет.

Пост упаковки назначается до индукции по минимальному reserved WIP, при равенстве — по ID поста. Reserved WIP включает tote в пути, входную очередь, обслуживание и BLOCKED_OUTPUT. Бронирование снимается после фактического принятия parcel в outfeed.

Tote возвращается в пул при `order_packed`, когда его содержимое передано parcel. Мгновенный виртуальный возврат пустой тары — явно подписанное допущение. При заблокированном выходе упаковщик продолжает занимать пост.

В loop допускается не более 96 tote при 112 ячейках. При увеличении пула до 112 и более необходимы ограничение допуска и проверка кольцевой блокировки. Parcel не ездит по tote-loop.

## Начальное состояние и сотрудники

Все 24 actor сверяются со staffing. Свободный actor без действий остаётся в `initial_pos`. Две машины связаны с двумя водителями: людей 24, а не 26.

В 600 адресах находятся 600 партий. Для каждого SKU: 2000 единиц на нижнем адресе и по 500 на двух резервных. Всего 600000 единиц. Число коробок на экране условно представляет наполнение партии и не равно количеству единиц товара.

Начальное состояние включает партии, остатки и резервы; tote `T001`…`T096`; ячейки и очереди; позиции сотрудников и текущие действия; reserved WIP постов; курсоры слияний; открытые и закрытые паллеты с таймерами.

Зарезервированные единицы входят в `on_hand` и не прибавляются к физическому остатку повторно.

## Грузы и баланс товара

Cargo содержит `cargo_id`, `kind` (`tote`/`parcel`/`pallet`/`lot`), `contents[{sku_id,quantity}]` и `order_ids`. Родительская паллета ссылается на parcels; при проверке баланса физическое содержимое считается ровно один раз. Событие transfer перемещает товар между locations, а не копирует его.

Для каждого SKU выполняется баланс:

```text
initial + accepted_receipts =
  on_hand_pickface + on_hand_reserve + receiving/staging
  + carried/tote + pack_WIP + parcel/pallet + dispatched
```

Запланированное поступление вне границы склада ещё не является accepted receipt. Груз, вошедший на receiving, попадает в ledger до начала обработки.

## Конечные очереди и паллеты

Вместимости: receiving queue — 8 паллет; reserve staging — 40 паллет; shipping buffer — 40 parcels; очередь закрытых паллет — 8. Открытая паллета одна. Два отгрузчика атомарно резервируют на ней места.

Если очередь закрытых паллет полна, заполненная открытая паллета ждёт закрытия и блокирует дальнейшую укладку. Таймер не создаёт вторую задачу. Паллета закрывается по 10 parcels или через 300 с после первого вложения. Неполный остаток ждёт собственного таймера; досрочное закрытие при drain в P0 не используется.

В P0 товар из reserve staging не пополняет active faces. При поступлении 20 паллет/ч в восьмичасовом опыте площадка на 40 паллет заполнится примерно через два часа и заблокирует приёмку. Это известное ограничение без replenishment, которое должно быть видно в отчёте. Основной часовой demo получает 20 паллет. Невидимое исчезновение груза не может устранять блокировку.

## Scenario и временная причинность

До сравнения A/B материализуются заказы, строки, `arrival_s`, поступления и канонические хеши. Одного одинакового seed недостаточно, чтобы доказать одинаковость входов. Строки заказа уникальны по SKU, quantity — целое число больше нуля.

Для большого сценария 200 SKU задаётся `provenance.kind=synthetic`. Значение `historical_partial_baskets` разрешено только при фактическом историческом источнике.

Синтетическая история — 56 дней: 42 train и 14 validation. После фиксации параметров итоговая модель обучается на 56 прошлых днях; test недоступен. Первые 28 дней, для которых ещё нет всех лагов, не являются обучающими targets. Подгонка по test gain запрещена.

Изменение входной интенсивности создаёт новый scenario. Внутри slotting comparison одинаковы заказы, поступления, config, начальные остатки и операции; различаются размещение и оплаченный план переносов. Опыт с изменением штата имеет отдельный `experiment_type`.

## Actions и состояния сотрудников

Action содержит `action_id`, `actor_id`, `state`, `operation`, `start_s`, `end_s`, `entity_id`. Для TRAVEL задаются `waypoints[node_id,pos,at_s]`, для остальных состояний — `pos`. Используется ровно один способ задания геометрии. Должно выполняться `end_s>start_s`; интервалы одного actor не пересекаются. Backend проверяет эти межполевые инварианты поверх schema.

Состояния: TRAVEL, BUSY_SERVICE, BLOCKED, WAIT_RESOURCE, IDLE. Примеры operation: pick, pack, scan, putaway, loading, tote_wait. Производительный труд — TRAVEL + BUSY_SERVICE; blocked показывается отдельно. Загрузка персонала учитывает всё время, когда сотрудник недоступен для новой задачи.

## Events и порядок обработки

Event содержит `seq`, `at_s`, `phase`, `kind`, `entity_id`, `payload`. Порядок — `(at_s,phase,seq)`, seq глобально уникален.

| Phase | Что обрабатывается |
|---|---|
| 0 | Завершения операций и освобождение ресурсов |
| 1 | Внешние arrivals и приём товара в ledger |
| 2 | Атомарные конвейерные переходы и допуск грузов |
| 3 | Закрытие паллет, назначение задач и начало обслуживания |
| 4 | Контрольная точка |

Учёт внутри phase завершается до выпуска snapshot и не создаёт повторного физического перехода груза.

Обязательное содержимое payload:

- `order_arrived`/`order_assigned`: order_id; для assigned также actor_id и tote_id.
- `stock_reserved`/`sku_picked`: order_id, sku_id, slot_id, lot_id, quantity; для picked также actor_id.
- `handoff_ready`/`tote_inducted`: order_id, tote_id, actor_id, induction_id; для inducted также target_pack_id и cell_id.
- `cell_entered`/`cell_exited`: cargo_id, cell_id, transition_id и from/to container_id. Пара событий описывает один атомарный transfer.
- `pack_started`/`order_packed`/`parcel_outfed`: order_id, pack_id, actor_id и tote_id/parcel_id после создания соответствующих сущностей.
- `parcel_scanned`/`pallet_sealed`/`order_dispatched`: order_id(s), parcel_id(s), pallet_id, actor_id; для dispatch также dock_id.
- `receipt_*`/`pallet_putaway`: receipt_id, pallet_id, sku_id, quantity, actor_id и ledger from/to.
- `actor_state_changed`: actor_id, state, operation, entity_id либо null.

Schema пока допускает произвольный payload object. Полная валидация для каждого kind обязательна при реализации exporter. Нынешнюю форму нельзя считать доказательством корректности готового движка.

## Replay, snapshots и доставка результата

События применяются при `at_s<=clock`; действия занимают полуоткрытые интервалы `[start_s,end_s)`. Snapshots каждые 30 с восстанавливают всё состояние, включая ready times, таймеры и курсоры слияний. Chunks охватывают по 60 с.

Seek: восстановить ближайший snapshot → применить события до target. Уже применённые события не дублируются.

`run.schema.json` задаёт полный inline run. Для доставки частями manifest содержит те же версии, хеши chunks и временные границы. После объединения результат логически эквивалентен inline. Полный chunk format фиксируется перед интеграцией; первый runtime может использовать inline.

## Завершение прогона и метрики

Status: complete / partial / failed. Termination: drained / unfulfilled_inventory / max_drain / deadlock / error. При stockout или незавершённых заказах `all_orders_makespan_s=null`.

Последняя отгрузка может завершиться раньше возврата погрузчика домой. Run может быть partial из-за заблокированной приёмки, даже если все заказы выполнены; причины показываются отдельно по подсистемам.

`packed_total` и `dispatched_total` различаются. Главный completed v2 означает dispatched. P95 рассчитывается методом linear по завершённым заказам и показывается рядом с completion rate и возрастом backlog. Utilization и интеграл очереди считаются на `[0,H)`. Неопределённые средние и отношения равны null. Отрицательные эффекты плана сохраняются.

Legacy completed означает packed; его нельзя переименовать в dispatched. Старый `verification_report.v1.json` относится к v1. Корневой `verification_report.json` проверяет новые материалы, а не работу готового приложения.

### Конкурентное закрытие паллеты

При full/timeout паллета получает SEAL_PENDING и запрещает новые reservations. Уже зарезервированные scan/placement завершаются; seal выполняется только после их окончания и получения места в sealed queue, forklift task создаётся один раз. При scan[296,304) и expiry300: pending300, seal не раньше304. Закрытая паллета неизменяема.

### Размер экспорта

Snapshot ссылается на неизменяемые catalog/layout и хранит изменяемое состояние. Клиент держит текущее окно и соседние chunks, а не историю всей смены. Проектные цели: raw payload для 1 часа ≤30 MB, event cache ≤64 MB; фактические bytes и peak heap ещё измеряются. Dictionary encoding и один atomic cell transfer допустимы с явным adapter в логические события; выборочная анимация не имеет права менять итоговые счётчики.
