# Граница A/B перед реализацией

Основание: 01_Technical_Specification.md, 03_3D_Scene_and_Replay.md,
04_Work_Packages_48h.md, contracts/README.md и JSON Schema. Подготовлено 06.11.2026.

## A — наша часть

Весь frontend, Blender/GLB, выбор SKU/slot, камеры, парный показ, replay,
состояния интерфейса, подключение API и сохранённых прогонов, visual QA.
Backend, модель спроса, планировщик, маршруты, длительности и финальные KPI — B.

Необходимый стек A уже подготовлен. Платный генератор, Meshy, NVIDIA Omniverse,
Unity/Unreal, ROS, БД и внешние AI API для этой части не требуются. Внешние
библиотеки ассетов Blender отключены; собственные повторяемые модели можно
сделать через bpy и существующий MCP. Их включение не является условием старта.

## Зафиксированная геометрия

- `schema_version=1.0`, `layout_version=qoyma-20x18-v1`.
- Метры, секунды, `[x,y,z]`, Y вверх; пол 20x18м.
- 20 адресов `S_A1_B1`…`S_A4_B5`, 31 узел, 33 неориентированных ребра.
- `initial_assignment`: ключ slot_id, значение sku_id. BUFFER не входит.
- Переставляются контейнеры SKU; стеллажи/граф не меняются.
- Позиция отбора и anchor коробки различаются. S_A1_B1: `(3,0,4)` и `(1.5,0.9,4)`.

## Минимальная поставка от B

Первое подключение возможно через один Run, валидный по run.schema.json.
Обязательны actors (включая простаивающего P2), полный initial_assignment,
scenario/provenance, config, WALK/PICK/DROPOFF/PACK actions, упорядоченные
events, orders_summary и metrics. Первый реальный Run должен заменять ручную
фикстуру без изменения её формата.

После этого нужны GET /api/catalog и POST /api/compare (допустимый cut line ТЗ),
а при полном API — forecast/plans. Для парного ответа ожидаются baseline_run
и candidate_run при одинаковых зафиксированных orders/config/layout. Полной
Comparison JSON Schema в исходном пакете нет: точную оболочку ответа нужно
закрепить с B при подключении, не изобретать отдельную несовместимую версию.

Переносы сейчас имеют seq, sku_id, from_location, to_location. Их времен/полилиний
в plan.example.json нет. До расширения поставки B допустим показ трёх шагов
переноса и рассчитанной стоимости; A не рассчитывает новый физический маршрут.

## Важные расхождения и ограничения

1. В одном абзаце contracts/README используется `distance_m`, но действующая
   Run schema и ручной пример используют `metrics.total_distance_m`.
   Клиент должен следовать Schema/фикстуре. Исходные файлы не изменены.
2. Исследовательские probe assignment могут иметь направление SKU→slot и другие
   node IDs. Не подавать probe JSON прямо в runtime; адаптер принадлежит B.
3. hand_checked_run содержит искусственные SAMPLE_* SKU. Реальный catalog —
   sku_master_20.csv; смешивать эти режимы нельзя.
4. В обычном исследовательском benchmark оба метода дали no-op на всех 20 днях.
   Акция 22382x5 — отдельный синтетический сценарий. Полный эффект акции,
   очередь упаковки и throughput ещё не посчитаны готовым backend.
5. Реальные продажи дают только ассортиментный срез: 1745 visits, 749 частичных
   корзин, 3.794% visits магазина; только 7 исходных накладных полностью покрыты.
6. В MVP нет stock decrement, столкновений работников и live WMS/IoT.

возврата/dropoff в 32.9666666667с; упаковка закончена в 57.0666666667с.
Tolerance 1e-6. Проверить seek `end → 6 → 18 → 0 → end` без двойного учёта.
Фронтенд интерполирует абсолютное время и готовые сегменты, не запускает свой
оптимизатор/очередь. Стоимость переносов учитывается отдельно от makespan.
