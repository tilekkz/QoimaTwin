# Визуальная сборка Qoyma Twin

Состояние на 07.11.2026. Этот документ описывает подготовленный визуальный пакет; ограничения численной интеграции остаются в [TWIN_INTEGRATION.md](TWIN_INTEGRATION.md). Ранние замечания о ещё не созданном дизайне в документах подготовки относятся к предыдущему этапу.

## Референсы и направление

До моделирования просмотрены все пять пользовательских изображений из папки `Qoyma_Twin/рефы`. Затем встроенным imagegen созданы восемь отдельных растровых листов. Все восемь листов были собраны до начала моделирования. Каждый показывает один согласованный объект в четырёх ракурсах; окружение показано как сборка склада. Полные исходные запросы сохранены рядом с изображениями:

| Семейство | Лист в `assets/references/` | Полный запрос там же |
|---|---|---|
| Стеллаж | `rack-bay-reference.png` | `rack-bay-prompt.md` |
| Коробка SKU | `crate-reference.png` | `crate-prompt.md` |
| Комплектовщик с тележкой | `picker-cart-reference.png` | `picker-cart.prompt.md` |
| Упаковочный пост | `packing-station-reference.png` | `packing-station.prompt.md` |
| Буферная платформа | `buffer-pallet.png` | `buffer-pallet.prompt.md` |
| Погрузчик | `forklift.png` | `forklift.prompt.md` |
| IBC-контейнер | `ibc-tote.png` | `ibc-tote.prompt.md` |
| Окружение склада | `environment.png` | `environment.prompt.md` |

Основной язык формы: объёмные low-poly миниатюры, небольшие фаски, матовая тёмная сталь, тёплый картон/дерево, сдержанные жёлтые детали безопасности и бирюзовые акценты. Модели сохраняют конструкцию, силуэт и материалы листов; это самостоятельная геометрия, а не попиксельное воспроизведение генерации. Согласованные метрические размеры имеют приоритет над перспективой на листах. Листы не используются как runtime-текстуры. Платные внешние генераторы не применялись.

## Исходники и runtime

Для каждого из восьми ID существуют индивидуальные `assets/blender/<id>.blend` и `frontend/public/models/<id>.glb`. Исходная `.blend` сохраняет отдельные редактируемые детали; GLB объединён по материалам для браузера. Воспроизводимые построители находятся в `tools/blender/build_*.py`, общий helper — `asset_common.py`.

Фактические значения ниже прочитаны из соответствующих `assets/blender/*.stats.json` после экспорта. Высота поста включает монитор; габариты окружения включают архитектуру, а не только пол.

| ID | Треугольники | Mesh-батчи | GLB, байт | Размер X × Y × Z, м |
|---|---:|---:|---:|---|
| `rack-bay` | 3 572 | 8 | 221 952 | 0,90 × 2,60 × 1,50 |
| `crate` | 604 | 7 | 39 752 | 0,55 × 0,45 × 0,65 |
| `picker-cart` | 7 056 | 13 | 408 652 | 0,639 × 1,70 × 1,182 |

Сумма восьми уникальных GLB — 2 927 348 байт, геометрии — 50 556 треугольников. Это не число треугольников или draw calls полного кадра: стеллажи, коробки и люди повторяются в сборке; браузер дополнительно объединяет статическую геометрию по материалам. FPS и бюджет парного просмотра этими числами не подтверждаются.

`tools/blender/assemble_warehouse.py` собрал общую редактируемую мастер-сцену `assets/blender/warehouse.blend` из восьми семейств с именованными slot/actor/service-узлами и anchors. Мастер-файл существует; общая экспортированная модель — `frontend/public/models/warehouse.glb`, 3 066 736 байт и 136 956 треугольников по `warehouse.stats.json`. Статистика экспорта содержит 375 mesh-узлов; это не число draw calls браузера после его объединения геометрии.

В одном браузерном виде склада — 72 draw calls, 136 956 треугольников (выше желательного ориентира 100k). 60-секундный замер интервалов requestAnimationFrame во время реального render loop дал median 144,93 FPS, p95 frame interval 7,1мс: Chrome156, Intel UHD/ANGLE D3D11, 1366×768, DPR1, статичные кэшированные тени. Измерено 8641 интервал; отчёт assets/performance-single-view.json. Это одиночная статичная сцена, не производительность будущего парного replay/симуляции; результат не является GPU timing query.

## Геометрия и смысл сцены

Канонический источник размещения — [contracts/layout.example.json](../contracts/layout.example.json), `layout_version=qoyma-20x18-v1`: метры, Y вверх, пол 20 × 18 м, четыре прохода, ровно двадцать постоянных адресов `S_A1_B1`…`S_A4_B5`, 31 узел и 33 ребра. Перестановка SKU меняет assignment, а не стеллажи или граф. BUFFER остаётся временным ресурсом и не становится двадцать первой ячейкой.

Стеллаж имеет верх рабочей полки Y=0,675; центр стандартной коробки — Y=0,9. Верх столешницы PACK — Y=0,85; пост ставится в `(9,0,0.6)`, буфер — в `(18,0,0.8)`. Origin комплектовщика находится на полу под работником, тележка выступает вперёд вдоль local +Z; ширина группы 0,639 м укладывается в лимит 0,8 м. Поворот glTF исправляющим вторым разворотом осей не добавляется.

Два человека стоят в иллюстративных позах. Погрузчик припаркован как деталь окружения; IBC также не является участником расчёта. Текущая визуальная сборка не воспроизводит историю движений и не доказывает работу replay, маршрутов, очереди упаковки, времени операций или KPI. Эти функции ещё требуют интеграции с Run/событиями по контрактам.

## Просмотр и контроль качества

Браузерный экран содержит общий обзор, вид сверху, вращение и приближение камеры, выбор стеллажа с приближением к адресу, отдельный режим осмотра каждого из восьми ассетов и галерею всех сгенерированных листов с переходом к 3D. Реализация: `frontend/src/app/WarehouseView.vue` и `frontend/src/scene/warehouse.ts`. Это описание реализованных элементов; итоговый browser smoke/performance QA фиксирует основной процесс отдельно.

Для каждого семейства подготовлены front/side/rear/three-quarter renders в `assets/previews/<id>/`. При сравнении с листами проверялись глубина, соединения, положение пола, опоры, колёса и согласованность ракурсов. Уже внесённые уточнения:

- У коробки разнесены совпадавшие поверхности рамки и этикетки на 0,0002 м при сохранении внешних размеров, чтобы убрать z-fighting.
- У комплектовщика добавлены соединённые плечевые полосы жилета и воротник; квадратная лицевая накладка заменена объёмной формой щёк/челюсти. Кисти замыкаются на реальной ручке тележки, все четыре кастера имеют вилки и оси. Высота 1,70 м и нижняя граница около Y=0 подтверждены экспортом.
- У погрузчика проверен контакт шин с полом; к отдельным звеньям подъёмных цепей добавлены непрерывные боковые элементы. Первоначальная ошибка отчётных габаритов была вызвана повёрнутыми bounding boxes после объединения: измерение исправлено на реальные мировые координаты вершин, геометрию ради этой ошибки не масштабировали.
- У поста проверены четыре опоры, нижняя полка, реальная толщина столешницы, опоры устройств, открытые клапаны коробки и лоток принтера. Отсоединённых кабелей нет.

Четыре ракурса поста просмотрены: конструкция и опоры прошли визуальную проверку. Финальные повторные четыре ракурса комплектовщика также просмотрены: форма лица уточнена, жилет соединён через плечи, воротник прикрывает переход шеи; кисти, ручка, кастеры и подошвы согласованы. Нижняя граница около Y=0 подтверждается экспортом, размеры и origin сохранены. Финальные исправления коробки и погрузчика проверяет основной процесс отдельно; их окончательный visual QA этим документом не закрывается.

Typecheck/production build и Khronos glTF Validator для всех десяти GLB (восемь семейств, calibration и warehouse) прошли: 0 errors, 0 warnings. Три Chrome smoke tests прошли: калибровка, отсутствие GLB с понятной ошибкой, полный обзор/приближение/восемь моделей/галерея/resize. Структурная проверка девяти новых GLB по фактическим binary POSITION, ground contact, габаритам, индексам и встроенным ресурсам прошла; отчёт — assets/visual-asset-checks.json. Повторная визуальная проверка исправленной этикетки и уточнённого персонажа завершена. Повторная проверка 113 численных/контрактных условий подготовки также прошла. Мастер открыт в live Blender, подтверждены двадцать selectable_slot и Unit Scale1.0.

## Пересборка

Из корня проекта: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/build-visual-assets.ps1 -Render`.
Скрипт строит ассеты и мастер последовательно в отдельных фоновых Blender-процессах,
не очищая текущую live-сцену. Затем `frontend: npm.cmd run build`,
`npm.cmd run verify:assets`, `npm.cmd run test:smoke`.

Исходные ТЗ, contracts, data и backend не изменялись; README дополнен актуальным статусом
поверх сохранённого исследовательского snapshot. Новая работа сохранена локально
в ветке codex/twin-environment. Реализация операций/событий/сравнения по ТЗ — следующий этап.

Граф `qoima-twin` обновлён; проверено покрытие 17 файлов нового кода. Recorded parse gaps
не обнаружены; `__pycache__` исключён штатно. Метаданные freshness снова помечены
metadata_changed даже после индексации, поэтому проверки опираются на прямое чтение,
реальное выполнение Blender/браузера и бинарную валидацию, а не полноту графа.
