## Concrete boundary

Refined inputs/checks: one object schema (not an8record catalogue) and one STANDARD_CARTON HU target example0.60×0.40×0.30m, with smaller physical unit and explicit per-unit/outer-HU tare ledger. Bind exact L12 version/content/private+public hashes and R03 target hash. Detailed orientations are proper signed-axis rotations; upright preserves local+Y. L09 upright_xyz_in_module maps only to identity cargo axes, never silently yaw90. Tags describe conditional compatibility, not resource availability/admission. Use installed local structural validation if available plus a narrow semantic runner; no installs/solver/SKU/lot/stock.

Define one namespaced versioned CargoArchetype record schema and a clearly synthetic example, bound to accepted L12 layout version/content hash. Separate physical unit, packaged handling unit and later lot/stock quantities. Include positive finite XYZ dimensions and kg masses, computed volumes, unit count per HU, packaging tare/gross mass identity, permitted orientation semantics (Y up), upright/fragile/stacking limits, required handler/equipment and allowed transport/storage tags, source of assumptions and reference target ID. Explain how L09 upright slot orientation maps to detailed cargo permutations; do not silently grant arbitrary rotation. Eight stable archetype IDs are known, but C02 adopts/fills catalogue separately; do not implement SKU mapping, inventory, admission solver or frontend UI here.

Use available local validation libraries or a small explicit semantic validator, with meaningful rejection of missing fields, zero/negative/nonfinite dimensions/masses, wrong computed volume/gross mass, conflicting upright orientation/stack limits and mismatched layout snapshot. Original R03 values are HU targets, not a claim all unit contents have those dimensions. Root directly reads schema/example/validator and runs checks before PASS. Keep implementation narrow so C02/C04 can start promptly.
