## PASS и проверка

Три уникальных port_id, положение, ориентация, service point и допустимые грузовые классы

Локальные критерии до создания proposal:
1. Ровно три уникальных IN ID в исходных boundary coordinates; direction inbound, unit inward normal и floor service node с namespaced semantic ID. Service point внутри protected approach на clear floor, не в storage/staging.
2. Явный cargo archetype matrix: W heavy/pallet/IBC/long/drum/fragile, N standard/pallet, E small/standard. Gate dimensions положительны, внутри 8 м envelope; clearance provisional до L05, не автоматический допуск гружёной техники.
3. Каждый порт содержит available equipment references, конечный bay/job limit, конечный handling-unit buffer с allocations в принятых staging rectangles, synthetic per-HU seconds и конечные open windows в elapsed seconds. Count limit не заменяет footprint/payload admission.
4. Все receiver/forklift ссылки ведут к одному shared policy. Проверка actual 24 actor IDs и F01↔FL01; никаких новых работников, локальных копий pools, трёх отдельных forklift pairs или implied throughput.
5. Численно сверить bounds/orientations/service clear floor, размеры opening в approach, staging access через reserved clear floor, buffers, service-rule coverage и units; source hashes/evidence. Это validation, не authored route graph.
6. JSON/MD фактически перечитаны; VERIFY до root review. Ни L04 implementation, ни geometry/route graphs/shared contracts не меняются.

Метод: фактический файл, измерение/расчёт либо meaningful runtime test по конкретному результату. Скрипт/export/отчёт исполнителя сам по себе не закрывает gate.
