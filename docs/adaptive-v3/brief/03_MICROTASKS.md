# QoimaTwin v3: микрозадачи для автономного исполнения

Эта карта исполняется, когда пользователь передаёт 01_START_CODEX.md как поручение на реализацию. Перед работой раскрыть карточки по 04_TASK_CARD_EXAMPLES.md.
Состояние проекта на момент постановки: ветка `codex/twin-environment`, HEAD `10496fd`, множество незакоммиченных изменений моделей и frontend.
Путь проекта: `C:/Users/izbas/Documents/Codex/2026-11-06/new-chat/work/QoimaTwin`. Перед исполнением проверить фактическое состояние: оно могло измениться.
Существующие наработки сохраняются. Микрозадачи не разрешают сбрасывать dirty files, переписывать общую историю или заменять файлы Армана.

## Режим выполнения

- Один пункт — один конкретный проверяемый результат. Ориентир для дочерней задачи: 8–35 минут; крупную задачу разделить по законченным результатам.
- Это 105 стартовых пунктов. Крупные модельные/интеграционные родители обязательно раскрываются в дочерние карточки по 04; это не обещание выполнить всё за восемь часов. Фактический срок зависит от качества исходников, доступных инструментов и параллельности.
- Статусы: TODO, READY, ACTIVE, VERIFY, FIX, PASS, BLOCKED. PASS требует указанного артефакта и фактической проверки.
- «Остановиться подробно» означает gate: закончить → осмотреть → сравнить с референсом/контрактом → исправить → сохранить → самостоятельно продолжить.
- Gate не означает ждать пользователя. Рутинные решения принимать по заданию; несовместимые варианты выбирать с короткой записью причины.
- При блокировке инструмента сохранить состояние, перейти на доступный маршрут и продолжить независимые задачи. Недостающие возможности не имитировать.
- Параллелить только задачи с выполненными зависимостями и разным ownership. Один live Blender не используется одновременно несколькими пишущими агентами.
- Backend Армана не реализовывать заново. Новые данные и контракты сначала описывать как изолированные предложения v3 с adapter boundary.
- Goal использовать лишь при наличии поддерживаемого механизма и при отсутствии конфликтующей активной цели. Checkpoint обязателен независимо от goal.
- Не создавать cron, дублирующие чаты или shell-loop самовызова. После реального ограничения сессии остаются сохранённые файлы и точный текст продолжения.
- Пути артефактов ниже задают структуру работы при запуске поручения.

## Условия v3, общие для всех этапов

- Основное здание 144×72 м, высота 8 м. Площадь 10368 м² — ровно в три раза больше 72×48 м; объём при той же высоте также утраивается.
- Масштабирование здания не масштабирует человека, погрузчик, коробку, толщину стены или расстояние между колёсами.
- Три входящих и три исходящих порта расположены на разных участках периметра и имеют реальные транспортные связи.
- 200 SKU описываются через восемь архетипов груза с размерами, массой, ориентациями и способом обработки.
- Типы хранения: SMALL, STANDARD, HEAVY, LONG, FLEX. Совместимость проверяется до стоимости размещения.
- Все новые массы, размеры, грузовые свойства и сценарные распределения — синтетические допущения, пока не получены реальные данные.
- Пример ограничения ручного переноса — 15 кг на человека; это явное модельное допущение, а не норматив безопасности.
- Художественный стиль v3: boxy cartoon low-poly, flat shading, ступенчатые фаски, крупные выразительные формы и немного функциональных деталей.
- Цвета ролей уже существуют в приглушённой палитре; задача — усилить различимость и добавить badge/legend, сохраняя цельный стиль.
- Новые референсы утверждаются визуальной проверкой до моделирования. Старые изображения не задают новые физические размеры.

## Правило перехода и отчёт

После каждого gate обновить checkpoint фактическими результатами, затем брать следующий готовый ID без ожидания ответа пользователя.
Задача, закрытая прежней работой, может сразу перейти в VERIFY: сначала осмотреть существующий результат, затем засчитать подтверждённое.
Документирование не заменяет моделирование: файл с описанием красивой модели не закрывает M/P-задачу.
Если сессия завершилась, в checkpoint остаётся одна точная инструкция продолжения с незавершённого ID, а не предложение начать всё заново.
Утренний отчёт коротко разделяет готовую визуальную часть, проверенные fixtures и интеграцию, ожидающую backend Армана.
