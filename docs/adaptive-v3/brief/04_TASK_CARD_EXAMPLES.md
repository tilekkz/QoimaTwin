# Карточки задач: обязательная глубина исполнения

Этот документ читается перед созданием TASK_BOARD. Таблица 03 — стартовая карта, а не разрешение выполнить сложное семейство за один непроверенный вызов.

## 1. Обязательный формат любой карточки

ID:
Название:
Родитель:
Владелец и файлы:
Зависимости:
Цель:
Входы:
Выходы:
Что сделать:
Ожидаемый результат:
Как проверить:
Что фактически получено:
Evidence:
Дефекты:
Исправления и повторная проверка:
Статус:
Следующий READY ID:

Поле «как проверить» записывается до исполнения. Поля actual/evidence заполняются после действительного просмотра/измерения. Если проверка не выполнялась, статус не PASS.

Перечень файлов без просмотра не является визуальной приёмкой. Успешный build без открытия viewer не является runtime-приёмкой.

## 2. Пример I01: сохранение настоящего исходного состояния

Цель: определить рабочую копию и отделить уже существующие изменения команды.

Входы: фактический workspace, git status, branch, HEAD, remote, существующие README/AGENTS.
Выход: work/v3/start-state.md.

Действия:
1. Установить фактический каталог.
2. Прочитать status и HEAD без очистки файлов.
3. Перечислить изменённые/неотслеживаемые файлы по областям.
4. Выделить файлы Армана и общие contracts.
5. Записать выбранную изоляцию и источник актуальной версии.

PASS: список соответствует реальному состоянию, прежние файлы сохранены, baseline не перепутан со старой research-копией.
Evidence: компактный вывод команд, дата и пути.
Дефект: отсутствующий frontend или устаревшая ветка возвращает карточку в FIX, а не приводит к созданию нового проекта поверх чужого.

## 3. Пример R05: новый персонаж, до построения mesh

Родитель R05 разделить, если невозможно получить согласованный результат за одну проверяемую итерацию.

Цель: новый boxy cartoon worker, пригодный для пяти ролей.
Зависимости: R01 PASS, I06 PASS.
Входы: новая style board, ролевая палитра 02, размеры человека и brief; прежние модели только как источник функций.
Выходы: reference-worker-v3.png, prompt.txt, reference-review.md.

Действия:
1. Составить prompt: квадратные крупные формы, одна конструкция, четыре вида, нейтральный фон.
2. Сгенерировать reference доступным image-generation tool.
3. Открыть его и проверить front/side/rear/three-quarter.
4. Проверить, что голова/конечности/руки имеют объём и один дизайн во всех видах.
5. Проверить cartoon/flat shading вместо реалистичной кожи/швов.
6. Выделить основной четырёхвидовой персонаж и цветовые варианты ролей.
7. При разрывах, лишних руках, разных пропорциях или чрезмерной округлости исправить reference.
8. Сохранить принятый reference_id.

PASS: согласованный трёхмерный персонаж нового стиля, нормальный метрический размер и различимые роли; реальный файл открыт и просмотрен.
Evidence: изображение и конкретное заключение по видимым признакам.
Следующая модельная задача закрыта, пока reference не PASS.

## 4. Как раскрыть M14: погрузчик

M14 — родитель. До исполнения создать минимум следующие дочерние результаты:

| ID | Один результат | Проверка |
|---|---|---|
| M14.1 | Размерная схема и origin/forward/anchors | Техника согласована с pallet/gate и нормальным размером водителя |
| M14.2 | Корпус, противовес и колёса | Front/side render: крупные blocky массы, четыре колеса касаются пола и соединены |
| M14.3 | Кабина, сиденье и рама | Side/rear render: водитель помещается, силуэт не полый/бумажный |
| M14.4 | Мачта, каретка и две вилы | Front/side: параллельные вилы, верные точки соединения и подъёма |
| M14.5 | Материалы и cartoon shading | Четыре вида сопоставлены с R06; нет случайного фотореализма |
| M14.6 | Pivot/rig и крепление паллеты | Проверены низкая/поднятая позиции и контакт вил с pallet |
| M14.7 | Runtime GLB | В браузере открыт финальный export; scale/axes/normals/materials совпадают |
| M14.8 | Pickup/load клип | На трёх контрольных timestamp груз не плавает и не проходит сквозь вилы |
| M14.9 | Parent gate | Все дочерние PASS, reference/render и runtime evidence доступны |

У каждого дочернего результата полная карточка из раздела 1. Не закрывать M14 по одному красивому three-quarter PNG.

## 5. Как раскрыть остальные модельные родители

Для каждого физически отличного asset:
1. Принятый reference и размерная схема.
2. Силуэт/основная конструкция.
3. Функциональные соединения/опоры.
4. Материалы/шейдинг и pivots.
5. Four-view compare и исправление.
6. GLB-export и browser check.
7. Действие/контакт, если asset движется.

M06 раскрывается отдельно для small/standard/heavy carton.
M07 — отдельно для tote и parcel.
M13 — отдельно для straight/turn/diverter.
P03 — отдельно для фигуры, cart, grip, walk, pick и handoff.
P09 — отдельно для dock module, large gate, shell/cutaway и разметки.

Повторяемый маленький декоративный болт не требует своей карточки. Другая форма груза, другой способ движения или отдельный файл модели требуют отдельного принятого результата.

## 6. Пример C06/C07: габариты и масса

Цель: кандидат сначала проходит совместимость, затем оценку маршрута.

Входы: fixtures F2 из 02, slot metadata, cargo metadata, orientation/clearance rules.
Выход: compatibility fixture и проверочный результат с reason code.

Действия:
1. Зафиксировать, что сравниваются handling unit и полезный размер адреса.
2. Проверить допустимые ориентации.
3. Проверить общую массу содержимого, а не массу одной единицы.
4. Выполнить три отрицательных/положительных случая F2.
5. В viewer показать отказ понятным текстом без изменения scale предмета.

PASS:
- A отклонён по dimensions.
- B отклонён по weight.
- В C одна коробка допустима, две отклонены по суммарной массе.
- Стоимость недопустимого назначения не используется как будто место подходит.

Evidence: исходные числа, expected/actual, reason code и один runtime screenshot отказа.
Если автоматический тест зелёный, но viewer уменьшает груз для влезания, задача возвращается в FIX.

## 7. Пример P02/P10: роль должна быть заметна

Цель: пять рабочих ролей различимы в полном складе, сохраняя один стиль.

Действия:
1. Применить role colors к vest/uniform, сохраняя actor_id.
2. Убедиться, что shared material не перекрасил остальных.
3. Добавить badge/legend и текстовую роль.
4. Открыть overview при 1366×768.
5. Открыть крупный план минимум двух похожих ролей.
6. Проверить обязательный сценарий смены разрешённой роли у cross-trained actor: событие назначения, переход к посту и восстановление роли при seek.

PASS: роль читается по цвету+badge; профиль/ID не теряется; остальные люди сохраняют свои материалы; смена роли не создаёт дополнительного работника.
Evidence: общий и крупный кадры, registry до/после.

## 8. Как раскрыть W14: осмысленное сравнение

W14 — родитель, а не задача «нарисовать два процента»:

| ID | Результат | Проверка |
|---|---|---|
| W14.1 | Сценарий и разрешённые различия | Явно перечислено, что фиксировано и что меняется |
| W14.2 | Materialized inputs | Orders/receipts/ports/weights совпадают; для slotting полный config одинаков. Для staffing отдельно фиксируются общий physical config и разрешённое отличие role_allocation_hash |
| W14.3 | Допустимый baseline | Нет специально испорченного или физически невозможного размещения |
| W14.4 | Допустимый candidate | Compatibility выполнена до расчёта стоимости |
| W14.5 | Переносы и цена | Есть последовательность transfer/swap и ресурсы; buffer совместим |
| W14.6 | Синхронный показ | Общий clock/camera, одинаковый выбранный SKU, видны направления груза |
| W14.7 | Объяснение результата | Причины, нулевой/отрицательный эффект и ограничения отображаются |
| W14.8 | Parent gate | Отдельно подписаны analytical/visual/actual engine result и показанный эффект |

F1 из 02 — ручная арифметика одного транспортного плеча. Она проверяет port weighting, но не доказывает новый throughput или прибыль.
Если backend ещё не поддерживает v3, экран не должен изображать выполненный DES.

## 9. Пример Q10: performance с сохранением качества

Вход: полный 144×72 layout, реальные assets,24 actor либо фактическая новая конфигурация, зафиксированный fixture.
Действия:60 секунд overview,60 секунд hero/follow; recorded viewport/device/browser/quality,medianFPS,p95 frame time,drawcalls,triangles/heap по доступным инструментам.

PASS: режим реально измерен; масштаб/данные сохранены; hero-модель остаётся принятого качества; исключения названы.
При провале сначала исправить culling/instancing/LOD/тени, затем повторить тот же замер.
Запрещённый обход: уменьшить число логических работников/груза или подставить FPS старой сцены.

## 10. Автоматический переход

После PASS:
- Сохранить actual/evidence и checkpoint.
- Выбрать следующую READY-карточку с выполненными зависимостями.
- Продолжить без сообщения «подтверди следующий шаг».
- Если появился дефект, открыть FIX с владельцем и связью на исходный ID.
- Зависимый parent возвращается из PASS, если дефект опровергает его критерий.

Таким образом агент подробно останавливается на качестве каждого результата, сохраняя самостоятельный непрерывный ход всей работы.
