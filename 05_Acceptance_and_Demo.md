# Qoyma Twin: приёмка большого склада и демонстрация

Версия 2.0, 07.11.2026. Критерии относятся к [основному ТЗ v2](01_Technical_Specification.md) и [контракту](contracts/README.md). Ниже записаны **ожидаемые результаты будущих проверок**, а не уже пройденные тесты приложения. Новая сцена и симулятор этой правкой документации не реализованы.

Тилек проверяет сцену, привязки и replay; Арман — расчёты, ресурсы и экспорт. Сквозную приёмку проходят вместе: сначала большой graybox и один полный заказ, затем массовый поток и модели. Маленький legacy не заменяет основной результат.

## 1. Обязательный gate масштаба P0

| Проверка | Требование |

| Адреса | 864 уникальных bin ID: 288 нижних pick faces и 576 верхних reserve slots |
| Ассортимент | 200 различных synthetic DEMO SKU; 200 занятых pick faces и 88 свободных |

| Запасы | 400000 units active и 200000 reserve, согласованные с ledger |
| Персонал | 24 человека: 12 отборщиков, 6 упаковщиков, 2 приёмщика, 2 отгрузчика, 2 водителя |
| Техника | Два погрузчика с грузовыми задачами; водители уже включены в 24 человека |
| Логистика | Три индукции, шесть упаковочных постов, приёмка, наземный резерв и отгрузка |
| Конвейер | 179 конечных метровых cells, включая loop из 112 cells; груз следует расчётным переходам |
| Тара и буферы | Pool 96 tote; pack buffer 4 на пост без обслуживания; shipping 40; приёмка 8; reserve staging 40 |
| Поток | Normal 240 arrivals/ч, Peak 600 arrivals/ч; выпуск определяется расчётом |
| Полный путь | Order проходит arrival→pick→belt→pack→pallet→dispatch; inbound pallet проходит приёмку→наземный резерв |

Все сотрудники существуют в расчётных ресурсах и actor registry. Обязательное число не означает непрерывную занятость: IDLE допустим. Фоновые прогулки не подменяют работу, размноженные meshes не создают SKU или остатки.

На слабом ноутбуке допустимы простые модели и один viewport с A/B toggle. Снижение качества не уменьшает размеры здания, штат, адреса или расчётный поток. Большой пустой павильон с двумя рассчитанными работниками не проходит приёмку.

## 4. Конвейер, finite queues и merge

Компактные фикстуры могут использовать несколько cells только для проверки движка. Основной run сохраняет 179 cells. Tick 1 с; новый груз на tick t впервые движется t+1. Overrides сохраняются с expected outputs.

| ID | Вход | Ожидаемый результат |
|---|---|---|
| C1 | Линия C1→C2→C3→выход; один tote принят C1 на t0 | C2 на t1,C3 на t2,выход t3; максимум 1 hop/tick |
| C2 | C1 занят, второй tote запрашивает вход | Второй остаётся у источника; occupancy≤1; запрос не теряется |
| C3 | A в C3,B в C2; выход закрыт до t5 | До t5 оба стоят; t5 A выходит,B может только перейти C3; B выходит не раньше t6 |
| C4 | Два источника на merge; target освобождается каждый tick; cursor=source1 | Гранты 1,2,1,2; максимум один новый груз в target/tick; одинаковый результат при повторе |
| C5 | Snapshot между грантами C4 | Следующий grant совпадает с непрерывным run; cursor не сброшен |
| C6 | Pack buffer полон, его tote у divert | Tote ждёт и блокирует хвост; нет рециркуляции, смены target или невидимой очереди |
| C7 | В downstream появилось место | Backpressure снимается по tick-правилам; один груз не получает несколько hop |
| C8 | Упаковка одного tote завершена | Tote возвращён в pool ровно один раз; физическая обратная лента не выдумана |

Проверить достижимость всех шести постов от каждой индукции. Target_pack_id неизменен; минимальный reserved WIP учитывает грузы в пути, в буфере, в PACK и BLOCKED_OUTPUT; tie по post ID. Каждый cargo имеет одну cell/location; transfer атомарный.

112 cells кольца и 96 tote общего pool сохраняют свободные клетки: ring occupancy≤96<112. Если pool увеличат, потребуется отдельная защита от полного кольцевого deadlock; прежний тест автоматически не переносится.

## 5. Упаковка и труд

| ID | Вход | Ожидаемый результат |
|---|---|---|
| K1 | Тестовый pack 10 с; 7 tote заранее распределены: 2 в PK01,по 1 в PK02…06; output свободен | Шесть PACK стартуют t0,заканчиваются t10; седьмой стартует t10,заканчивается t20. Суммарная очередь после dispatch=1, сумма ожиданий 10 с |
| K2 | В посте 1 service + 4 waiting; приходит шестой tote | Шестой ждёт вне buffer; capacity 4 исключает service; blocking виден |
| K3 | PACK окончен t10,outfeed закрыт до t15 | packed=t10; packer BLOCKED_OUTPUT[10,15); новый PACK не раньше принятия output |
| K4 | K3 | Tote release t10, station reservation сохраняет blocked parcel до outfeed accept t15 |
| K5 | Действие пересекает конец H | Shift utilization учитывает пересечение с [0,H); drain за H не входит numerator |

Queue maxima измеряются после мгновенного назначения свободным ресурсам. Time-weighted mean=интеграл длины очереди/H, не среднее её значений в eventlog. Активный труд=TRAVEL+BUSY_SERVICE; blocked сохраняется отдельно.

## 6. Запасы и сохранение груза

| ID | Вход | Ожидаемый результат |
|---|---|---|
| I1 | Pickface X содержит 2 units; заказы qty2 и qty1; replenishment нет | Первый резервирует 2; второй получает unfulfilled_inventory; отрицательных остатков и бесконечного ожидания нет |
| I2 | I1 до PICK | on_hand=2, reserved=2; физических units всего 2, не 4 |
| I3 | I1 после PICK | on_hand=0, reserved=0, tote=2; физическая сумма осталась 2 |
| I4 | Заказ X qty2 + Y qty1; Y отсутствует | Не резервируется и не списывается ни одна строка; частичного исполнения нет |
| I5 | Initial X=5, accepted receipt=3, затем 2 units отгружены | On hand=6, dispatched=2, WIP=0; баланс 5+3=6+2=8 |
| I6 | Receipt вне заполненной приёмки | Нет в accepted_receipt_units и внутреннем ledger |
| I7 | Active X=0, в ground reserve принято 500 X | Без replenishment active остаётся 0; недоступный заказ не исполняется из резерва |
| I8 | PACK/reset/seek | Units переходят между состояниями; товар не удваивается |
| I9 | Swap до смены | SKU перемещается вместе с lot; reserve assignment не меняется; buffer пуст до/после |

Для каждого SKU на каждом проверяемом timestamp:

`initial_units + accepted_receipt_units = on_hand_pickface + on_hand_reserve + receiving_staging + reserve_staging + carried_or_tote_units + pack_wip_units + parcel_units + dispatched_units`.

Reservation — атрибут части on_hand, не дополнительное физическое количество. Товар имеет одно location/status, изменения ledger атомарны. Для тары: `available_totes + allocated_totes = 96`. Allocated включает tote у работника, на ленте, в очереди и в PACK до release. Parcel после PACK не удерживает возвращённый tote.

| ID | Вход | Ожидаемый результат |
|---|---|---|
| T1 | Пустые orders/receipts | Нулевые суммы/очереди; null для неопределённых mean/p95/ratios; ошибки нет |
| T2 | H истёк до dispatch одного заказа | Заказ в backlog_at_H; поздний drain не подменяет shift throughput |
| T3 | Остались только unfulfilled_inventory, полезной будущей работы нет | Run partial с причиной, all_orders_makespan_s=null; нет вечного ожидания completed==arrived |
| T4 | Неустранимый blocking или max_drain=7200 | Partial с причиной и сохранёнными locations; фиктивных dispatches нет |
| T5 | Завершена часть заказов | P95 linear по завершённым рядом с completion rate, backlog count/age и причинами отказов |
| T6 | Offered load=600/ч, ресурсы не справляются | Arrivals=600 сохранены; меньший dispatch и растущий backlog допустимы |

Генератор создаёт ровно 240/600 arrivals за час и 1920/4800 за 8 часов. Эти числа не означают достигнутую производительность. Если не всё отгружено, last_dispatch_s может быть определён, а all_orders_makespan_s=null.

Backlog_at_H включает все поступившие к H и ещё не dispatched заказы; отдельно показываются unfulfilled_inventory и admitted WIP. Packed, dispatched и отказ по запасам разделены. Не складывать активный труд, blocked и ожидание клиента в одну «экономию часов».

## 9. Планировщик и честность сравнения

| ID | Вход | Ожидаемый результат |
|---|---|---|
| P1 | No-op, те же inputs | Relocation=0; те же assignment/lots; одинаковые содержательные events/metrics |
| P2 | Один occupied-pair swap | Три transfers, шесть take/place; SKU/lots сохранены; buffer свободен |
| P3 | До 2/8 swaps | Не более 4/16 разных SKU; каждый затронут не более раза; только ground faces |
| P4 | Gross surrogate gain меньше цены переносов | Выбран no-op; отрицательный test effect не скрыт |
| P5 | Relocation через rack shortcut | План отвергнут; полный путь по edges, обе ориентации обмена проверены |
| P6 | План по forecast ухудшил test | Факт сохранён; лучшая фактическая попытка не выдаётся за решение до смены |

В slotting опыте совпадают hashes layout/config/orders/receipts, начальные количества SKU, операции, routing и failure schedule. Различаются assignment и оплаченный relocation. Inputs материализуются до запуска; seed сам по себе недостаточен. Lots следуют SKU, а не старому адресу.

Staffing experiment имеет отдельный type: 14 pickers+4 packers против 12+6 с общим штатом 24. Его эффект не подписывается «AI-размещение».

V2 normal/peak/promotion помечены synthetic и собственными hashes. Forecast cutoff предшествует test; lags/rolling используют прошлое. Test не выбирает SKU, hyperparameters, shortlist или выгодную дату. WAPE агрегируется по суммам ошибок/фактов; дневные p95 не усредняются в «общий p95».

## 10. Hash, replay и восстановление

1. Run ID зависит от нормализованных содержательных inputs и engine version; wall time/request timestamp не влияют. Повтор inputs даёт тот же результат.
2. Events упорядочены `(at_s,phase,seq)`, actions полуоткрытые `[start,end)`. Backend и frontend совпадают на точной границе.
3. Snapshot содержит actors/cargo, остатки/reservations, cells, queues, tote pool, orders, pallets, station reserved WIP, merge cursors и таймеры.
4. Seek 10→80→20→80 даёт тот же state hash, что непрерывный run до 80; PICK/receipt/dispatch/tote release/seal не удваиваются.
5. Граница chunk/snapshot не теряет и не повторяет event. Клиент не начинает новую симуляцию при загрузке следующего chunk.
6. Pause останавливает clock; playback speed/FPS не изменяют KPI, порядок заказов или merge.
7. Во время PICK/handoff/blocked worker стоит; задержанный tote стоит на своей cell, а не ездит по декоративной траектории.
8. A/B toggle сохраняет time/camera/selection; завершившийся вариант остаётся в final state.
9. Reset восстанавливает initial inventory, pool, pallets, queues, trails и counters без stale state.
10. Mismatch schema/layout блокирует показ с понятной ошибкой; v1 без явного adapter не растягивается в v2.

## 11. Визуальная проверка и производительность

- Линейка 1 м, оси и размер человека совпадают после GLB export; anchors отличаются от layout не более 0.02 м. Global scale не масштабирует людей вместе со складом.
- В обзоре читаются 12 проходов, приёмка, активный конвейер, 6 постов и отгрузка; крыша не закрывает работу. Адреса и люди совпадают с registry.
- Видимые коробки условно показывают fill; число meshes не приравнивается к units. Верхний резерв и отсутствие auto replenishment подписаны.
- На целевом ноутбуке зафиксировать устройство/браузер, viewport 1366×768, quality и run. За 60 с массового replay замерить median FPS/p95 frame time; цель ≥30 FPS. Это ещё не полученное измерение.
- При низкой скорости упрощать meshes/materials/shadows/labels, использовать instancing/LOD и один viewport; не менять масштаб операционной модели.
- Нет WebGL — понятная ошибка/2D; нет backend — error либо «сохранённый расчёт». Новые параметры не применяются к старому run.

## 12. Готовность к защите

- Production build и backend запущены по инструкции из чистого терминала.
- Runtime assets и run chunks локальные; основной показ не зависит от CDN/API.
- Каждый gate имеет inputs, expected, actual и status. Нереализованное отмечено «не проверено», а не pass.
- Большие normal/peak прогнаны; ledger, queues, labor, dispatch и termination reason совпадают с экраном.
- UI/manifest показывают synthetic. Старые UCI20SKU числа остаются в historical reference со своей геометрией и ограничениями.
- THIRD_PARTY_NOTICES содержит реально использованные материалы; ключей и приватных данных в bundle/repository нет.
- No-op, нулевые и отрицательные результаты не скрыты; неподтверждённых заявлений о прибыли или реальном клиенте нет.
- Резервная запись соответствует проверенному большому run; сохранённый расчёт не выдаётся за новый online-run.

| Время | Показ |
|---|---|
| 0–15 с | Обзор 72×48 м: 24 сотрудника, 200 SKU, приёмка, conveyor, отгрузка. Подпись synthetic и единый источник движений |
| 15–30 с | Один order: worker→tote→belt→pack→pallet; разница packed/dispatched |
| 30–45 с | Очередь, blocked участок и роли: входной поток не равен выпуску |
| 45–60 с | Forecast, no-op/2/8 swaps, SKU и цена физических transfers; нет полезного плана — отказ от лишнего переноса |
| 60–78 с | Одинаковый materialized stream, A/B toggle на общем clock; путь, active labor, blocked, dispatch |
| 78–90 с | Фактические итоги, completion rate и ограничения. UCI — реальные частичные корзины; основной 200 SKU поток synthetic; сбережения клиента ещё не измерены |

Момент очереди выбирается из сохранённого проверенного run, а не имитируется константами KPI. Promotion имеет подпись known multiplier/scenario ID. Короткий 10–15-минутный run при той же интенсивности не выдаётся за смену 8 часов.

## 14. Вопросы жюри

«Почему двойник?» — одна адресная геометрия, ресурсы, остатки и события управляют расчётом и 3D. Пока это операционная модель без live-связи с физическим складом.

«Где AI?» — CPU-прогноз visits, сравнение с mean28 и решение до раскрытия будущего. У synthetic 200 SKU свои результаты; старые ML-метрики не наследуются.

«Откуда 240/600?» — заданная нагрузка генератора; фактический dispatch/backlog определяется симуляцией.

«Все 864 ячейки участвуют?» — все адресные и имеют состояние заполнения; отбор снизу, верхний резерв содержит начальный stock. Auto replenishment и подъём на ярусы вне P0 и подписаны.

«Конвейер просто анимация?» — finite cells, merge, target stations и backpressure; клиент проигрывает расчётные transitions.

«Почему не популярное ближе?» — это ABC baseline; проверяем добавочную пользу ограниченных переносов с полной ценой.

«Меньше ходьбы — больше отгрузок?» — не обязательно: packing/shipping могут ограничить выпуск. Путь, труд, blocked, packed и dispatched разделены.

«Что нужно для пилота?» — реальный план, адреса/остатки, полные заказы/приходы/отгрузки, роли/ёмкости/замеры операций; затем калибровка и проверка на смене.
