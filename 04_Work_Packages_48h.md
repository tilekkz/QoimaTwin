# Тилек и Арман: зоны ответственности и 48 часов

Оценка: примерно 25 часов предметной работы на человека плюс 3 часа совместной интеграции/проверки. Это ориентир для двух человек, работающих с AI-помощниками, а не обещание срока. В 48 календарных часов остаётся время на сон и резерв. При меньшем доступном времени действуют сокращения ниже.

## Тилек: 3D, цифровой двойник, клиент и воспроизведение

Владелец `frontend/src/scene`, `frontend/src/replay`, `frontend/src/app`, `frontend/public/models`, исходников Blender и визуальной документации. Основной профиль — моделирование и 3D, но роль включает связывание сцены с данными, интерфейс и визуальную проверку. Если человек умеет только моделировать и вообще не готов править TS даже с AI, это не равное разделение: тогда придётся сократить интерфейс до одного вида и заранее рассчитанного JSON.

| Задача | Часы | Конкретная поставка | Приёмка |
|---|---:|---|---|
| A1. Запуск донора, удалить нерелевантные панели/AGV-циклы | 2 | Минимальный Vue/Three экран, камера, loader | Работает production build, нет декоративных KPI |
| A2. Graybox и калибровка метра/осей | 2 | Пол, 20 секций, PACK/BUFFER, debug graph | Проверочный маршрут виден и не режет стеллажи |
| A3. Blender-модули и GLB | 4 | Rack bay, crate, low-poly picker/cart, pack station, исходный .blend | Единицы/IDs/anchors совпадают с manifest |
| A4. Сцена и связывание адресов с SKU | 3 | Загрузка/инстансы, label, выбор SKU/slot, plan highlights | SKU меняет место, slot сохраняет адрес |
| A5. Replay по фикстуре и реальным событиям | 5 | Clock, walk/pick/dropoff, pause, reset, seek, trail | Точное положение на заданных временах, нет двойных событий |
| A6. Интерфейс сравнения и планов | 4 | Два viewport либо резервный toggle, KPI/таблица, запросы API | Общие clock/camera; цифры из результата Армана |
| A7. Производительность и ошибки | 3 | Low mode, состояния loading/error, тест на ноутбуке | Читаемо 1366×768; зависание/ошибка не дают пустой экран |
| A8. Демо и передача | 2 | Короткая запись, 3 скриншота, инструкция запуска клиента | Демо повторяется из чистого состояния |
| Итого | 25 | | |

Тилек не должен обучать модель, рассчитывать оптимальный путь, определять длительность отбора или изобретать KPI. Он может работать по приложенной искусственной фикстуре до появления backend.

## Арман: кодовая логика, архитектура, данные, модель, симуляция и API

Владелец `backend`, подготовки `artifacts`, численных тестов и backend-документации. Канонический JSON контракт и shared layout меняются только после согласования с Тилеком. Готовые агрегаты и CPU-probe в пакете уменьшают начальную работу, но не заменяют интеграцию.

| Задача | Часы | Конкретная поставка | Приёмка |
|---|---:|---|---|
| B1. Данные и reproducibility | 2 | Подключить готовые CSV, проверить manifest и фильтры | Cutoff, SKU selection, hashes и coverage воспроизводятся |
| B2. Граф и маршруты | 3 | 31/33 graph, Dijkstra, nearest-neighbor, route export | Ручные 8/21.2 м проверки, путь только по рёбрам |
| B3. Два комплектовщика и упаковка | 5 | SimPy процессы, FIFO, состояния заказов, интервалы | Полный цикл и ручной однозаказный результат |
| B4. Прогнозы и backtest | 3 | Фиксированный CPU-ML + lag7/mean28, 20 дат | Нет future leakage; результаты не подменены лучшим днём |
| B5. ABC и до двух обменов | 4 | 0/1/2-swap планы, transfers, стоимость | Буфер пуст в конце, ≤4 SKU, нет выгодного плана -> no-op |
| B6. Парное сравнение/API/артефакты | 3 | catalog/compare минимум, общий scenario hash, JSON | Входные заказы одинаковы, клиент видит реальные события |
| B7. Проверки и массовый прогон | 3 | 20-date result CSV, sanity cases, README | Сохранены положительные/нулевые/отрицательные итоги |
| B8. Офлайн-набор и объяснение результата | 2 | Demo JSON, assumptions, таблица фактов | Запускается без LLM/внешнего API, числа совпадают |
| Итого | 25 | | |

Арман не должен параллельно строить красивый frontend, делать скелетную анимацию или переписывать донор в другой стек. Он отдаёт небольшие законченные пакеты данных, а не огромный незавершённый backend в последний час.

## Совместные контрольные точки

| Календарный срок от начала | Тилек | Арман | Общий результат |
|---|---|---|---|
| H0–H1 | Проверка донора/Blender | Проверка данных/окружения | Заморозить координаты, ID, единицы, контракт, стек |
| H1–H4 | Graybox + loader + упаковка | Graph + ручной маршрут + каркас run result | Первое движение на искусственной фикстуре |
| H4–H8 | Повторяемые модели и ID | Два picker + pack queue | Реальный завершённый заказ на серых кубах |
| H8–H12 | Pause/reset и события picking | Экспорт событий и KPI, первые API | Один законченный сквозной сценарий, пусть некрасивый |
| H12–H18 | SKU labels, trails, панели | Прогноз, ABC, swap-cost | План меняет размещение; метрики пересчитаны |
| H18–H24 | Парный вид/общая камера | Все методы на одинаковом потоке | Первый честный A/B и проверка чисел |
| H24 | Оценить оставшийся фронт | Оценить оставшуюся математику | Применить cut line, заморозить новые функции |
| H24–H34 | UI/low mode/seek QA | 20-date backtest/edge cases | Стабильная сборка и таблица всех результатов |
| H34–H40 | Демо/скриншоты | Офлайн JSON/assumptions | Чистый локальный запуск на ноутбуке защиты |
| H40–H44 | Повторить выступление | Проверить цифры и ответы | Две успешные репетиции без интернета |
| H44–H48 | Резерв | Резерв | Только исправления критических дефектов |

Таблица задаёт доступность поставок, а не непрерывную работу без сна. Окна отдыха согласовать после первого сквозного прогона; второй человек должен иметь сохранённую фикстуру и инструкции.

## Правила параллельной работы

1. Тилек и Арман не редактируют чужую директорию без сообщения. Договорённости о `shared/layout` и `shared/contracts` фиксируются коротким changelog, не устным «я там чуть масштаб поменял».
2. H1: Тилек получает приложенные layout + hand-check run. H8–H12: Арман заменяет фикстуру реальным run той же schema_version. Тилек меняет URL источника, а не переписывает проигрыватель.
3. Товар хранится в assignment, а адрес в layout. Изменение оформления GLB не меняет slot_id или пути.
4. В первые 12 часов интегрироваться каждые 3–4 часа по одному законченному заказу. Не ждать готовности всех моделей/всех метрик.
5. В PR/commit описывать конечное поведение и проверку. Не переносить целиком чужой WMS ради готового названия функции.
6. Несовпадение версий или координат останавливает новый прогон. Не «чинить» scale на стороне клиента без изменения manifest.

## Cut line: что сокращать, если не укладываемся

Порядок сокращения:

1. LLM объяснения, деньги, импорт пользовательских CSV и произвольные настройки.
2. Текстуры, стены/крыша, декоративный транспорт, сложная походка, постэффекты.
3. Два viewport заменить одним с A/B toggle и общей сохранённой шкалой времени. Итоговая таблица обоих вариантов остаётся рядом.
4. Раздельные forecast/plans endpoints заменить готовым catalog и одним compare; фактические расчёты и версии сохраняются.
5. Произвольную перемотку заменить надёжными reset/pause и несколькими точками времени, если полный seek не успевает пройти проверку.
6. Оставить одну основную дату для живого опыта; остальные 20 дат показать из реально выполненного offline benchmark. Не изображать сохранённые результаты новым онлайн-расчётом.

Нельзя сокращать: одинаковые заказы для A/B, маршрут по проходам, возврат/упаковку, стоимость переносов, временное разделение данных, простой baseline, честные нулевые/отрицательные результаты и маркировку модельных допущений. Именно эти свойства отличают рабочий прототип от заранее нарисованной анимации.

## Готовые задания AI-помощникам

Для Тилека: «Реализуй только visual client и 3D-часть цифрового двойника по `01`, `03` и `contracts`. Владей frontend и Blender assets. Сначала воспроизведи hand_checked_run.json, затем подключи API. Не вычисляй собственные KPI/пути, не меняй IDs и не редактируй backend. Арман работает параллельно над кодовой логикой и архитектурой; сохраняй его изменения».

Для Армана: «Реализуй кодовую логику, архитектуру и backend по `01`, `05` и `contracts`. Используй подготовленные данные, фиксированный ABC и 20-date temporal evaluation. Сначала graph + one-order simulation + exporter, затем прогноз и swaps. Владей backend/artifacts; не меняй frontend/GLB/контракт без согласования. Тилек работает параллельно над 3D и цифровым двойником; сохраняй его изменения».
